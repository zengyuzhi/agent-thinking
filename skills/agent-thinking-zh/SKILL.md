# Agent 思维方法

下面十二张方法卡片能应付大多数情况，每张写明要做什么、留下什么证据。两份参考文件放着完整版，只有下面某一步让你去查时才读对应的一节。

- [references/methods.md](references/methods.md) 收录 27 条思维方法，有背景和可复制的提示词，每条一个 `### N. 名字` 标题。每张卡片注明它取自哪几条。
- [references/techniques.md](references/techniques.md) 按任务类型整理提示词技巧，分 A 到 H 八节，末尾有一份可放进 CLAUDE.md 或 AGENTS.md 的合并版提示词。

用用户提问的语言回复，进度更新也一样。你写出来的提示词也用同一种语言，除非用户另有要求。

## 1. 定模式

读用户调用这个 skill 时附带的文字。Claude Code 会把这段文字填在这里：$ARGUMENTS。其他 Agent 里，它就是调用这个 skill 的那条用户消息。没有附带文字时，对象是当前对话里正在做的任务。

- **套用**。文字描述一件要做的事。你自己按选中的卡片完成它，见第 4 步。
- **写提示词**。文字要求写提示词、交给某个 Agent、写进 CLAUDE.md 或 AGENTS.md。你只产出提示词，不执行任务，见第 5 步。
- **点名**。文字点了一条或几条方法的名字。只用被点名的方法。名字对得上某张卡片就用卡片，对不上就在 methods.md 里 grep 它的标题，只读那一节。跳过第 2 步。
- **咨询**。文字问哪些方法或做法适合，没有要你动手。走第 2 步，然后按第 6 步回复，不改任何东西。

任务是派发其他 Agent 去干活时，你作为主会话按套用模式走，给每个 Agent 写的简报按第 5 步写。

如果没法用一句话复述任务和模式，先问用户一个问题再继续。

## 2. 挑卡片

只根据任务文字逐个回答下面的问题，不要为了回答去打开文件。暂时答不上来的算“否”。答“是”的卡片进入候选。

| 问题 | 卡片 |
|---|---|
| 需求含糊，或者有几种理解？ | 澄清 |
| 要修 bug 或者别人报告的故障？ | 复现 |
| 原因不明，有几种可能？ | 诊断 |
| 要依据文档、笔记、之前的总结或记忆里的 API 行事？ | 疆域 |
| 任务大，有几部分要拆开或排顺序？ | 拆解 |
| 要加新代码、新功能或新依赖？ | 最简 |
| 要删或重写看似多余的代码、检查或配置？ | 篱笆 |
| 改动可能弄坏原本正常的东西，或者用测试、指标来判定完成？ | 基线 |
| 要上线、要改别人依赖的接口，或者失败代价高？ | 事前验尸 |
| 要在几个方案里选一个，或者需要别人来检查？ | 审查 |
| 工作会跨会话、跨上下文压缩或者要交接？ | 任务记录 |

候选最多留三张，派发 Agent 时最多五张。留下能防住最可能、代价最高的失败的那几张。项目自己的规则或者已留下的卡片已经要求了某张卡片的动作，就去掉这张。证据账本卡片永远适用，不占名额。

**任务文字里写明了可运行的检查（测试命令、验证器、构建），并且只要求一处有边界的改动时**，只留证据账本，并用一行说明原因。其他卡片在这些情况下才划算：没有可运行的检查，有破坏性或对外的操作，多个 Agent，原因不明，或者工作跨会话。

你接下来的第一条输出就是下面这条选用消息，在它之前不调用任何工具。任务是解释讲解、画架构图、调研、长任务或界面文案时，再加一行写明 techniques.md 的对应小节（B、D、F、E 或 H），开工前读完。发完继续做，不用等回复。第一次看过代码之后，可以增加或换掉一张卡片，并说明原因。

```
选用
- 复现：防止修了一个从没亲眼见过的症状。多做的事：改之前先跑一遍失败的用例。证据：命令和输出，修复前后各一份。
- 证据账本：每条验收标准标明已验证、失败或未验证。
- 技巧：H 界面文案（只在有对应小节时写）。
```

## 3. 卡片

**澄清**（方法 2）。写出你对需求的理解，以及拿不准的词和范围。能从代码、测试和提交历史里弄清的先自己弄清。只问答案会改变实现方式的问题，一次一个，按重要性排序。证据：问了什么、得到什么回答，或者你选定的假设和理由。

**复现**（1、3）。改任何东西之前，先复现故障，记下命令和实际输出。复现不出来就说明，写出改用什么检查，只有任务提供了这样的检查才继续。说明你怎么确认找到的是原因而不是症状。修完后重跑同一条命令。证据：复现命令，以及修复前后的输出。

**诊断**（13、14、15）。有几种可能的原因时，挑能把它们区分开的实验，等实验指向原因之后再改代码。每一轮简短记录：怀疑什么、跑了什么命令、看到了什么、结论。找到直接原因后继续追问为什么，直到找到一个修好后能防住这一类故障的原因；有几条分支就都列出来。搜不到不等于不存在，说明你的检查方法漏掉它的可能有多大。证据：这份记录。

**疆域**（4）。依据文档、注释、笔记、之前会话的总结或记忆里的 API 行事之前，先拿当前的代码、配置或命令输出核对一遍。第三方 API 对照已安装版本的官方文档。文档和代码不一致时，代码说明的是实际怎么运行，不一定是本来的意图：用需求、测试、调用方和提交历史来判断，并把不一致的地方列出来。证据：你依据的每条说法，以及拿什么核对的。

**拆解**（5、6）。把任务拆成互不重叠、合起来覆盖全部的子任务，每个写明输入、输出和检查方法。标出依赖关系，有先后依赖的按由易到难排。证据：这份清单，做完一项勾一项；长任务写进 TODO.md。

**最简**（7）。先用现有代码、标准库或已安装的依赖，再考虑写新代码。不加没人要的功能、选项或抽象层。觉得需要更复杂的方案时，先说明简单方案哪里不够。证据：每样故意没做的东西写一行。

**篱笆**（11）。删除或重写看似多余的东西之前，查清它为什么存在（git log 或 blame、关联的 issue 或 PR），找到所有引用它的地方，说明删了以后什么会坏。查不到历史时，改用测试、调用方和运行时行为判断，并写明还有哪些不清楚。如果是用户要求删的，这些检查决定怎么删，不决定删不删。不是用户要求的，又找不到存在的理由，就列出来让用户决定。证据：每个被删项查到的历史和引用。

**基线**（16、17）。改之前，跑覆盖受影响行为的检查，加上仓库要求的检查，记下结果。改完后重跑同样的命令。原来通过的检查应该仍然通过，指标不应变差；取舍避不开时报告出来，不要悄悄做。测试是用来验证目标的，不是目标本身：除非你证明某个测试本身错了并且说明，否则不改、不跳过、不删测试，也不硬编码期望值。证据：同样的命令在修改前后的结果。

**事前验尸**（9、10）。假设这个改动上线一个月后失败了。列出最可能的原因，包括对调用方、数据、性能和用户的二阶影响。每条原因现在就加一个测试、防护或监控，或者说明为什么接受这个风险。证据：每条原因及其对策，指向新加的测试。

**审查**（18、19、20、21）。找一个没参与这项工作的审查者，只给它原始需求和最终产出。它的任务是证明这份工作是错的，用反例输入、代码位置或复现步骤说话，只报告影响正确性或违反需求的问题。没有第二个 Agent 时，自己单独做一轮：至少构造一个专门用来弄坏这个改动的输入，并且真的跑一遍。要在几个方案里选时，先给每个方案写出最有力的理由。多个 Agent 判断同一件事时，各自先给结论再看别人的；有分歧时用一个能区分双方的检查来定，不投票。证据：发现的问题及其证据，或者检查过哪些方面、没发现问题。

**任务记录**（1；techniques E）。维护一份记录：目标、验收标准、用户最新的决定、改变了的假设、每条标准的状态、阻碍和下一步。优先用已有的任务、计划或进度文件；只有任务本来就要改文件时才新建。在交接时、上下文压缩前和范围变化时更新。恢复工作时先重读它，和当前文件核对后再继续，每个阶段确认自己还在解决最初的问题。证据：结束时仍然是最新的这份记录。

**证据账本**（22、23、25、26；永远适用）。从用户的要求、任务本身和仓库规则里列出验收标准。每条标明已验证、失败或未验证，旁边放上产物：你跑的命令和它的输出、文件，或者 diff。检查只有在最后一次可能影响它的修改之后跑的才算数。陈述时把观察到的和推断的分开。每条必需的标准都有产物时报告做完；否则报告还剩什么。最后列出不确定的地方：没测过的场景、假设、可能过时的信息，各自写明如果错了会影响什么。一份结果可以支撑几条标准，指向它就行，不用重复贴。

## 4. 套用模式

按选中的卡片完成任务，最后给出证据账本。遇到用户没批准过的不可逆操作，比如删数据、推送、对外发送任何内容、改权限，先停下来问。

解释讲解、画架构图、调研、长任务或界面文案，再读 techniques.md 对应的小节（B、D、F、E 或 H），按 `## ` 标题查找。

派发 Agent 时，每个 Agent 只拿和它那部分相关的卡片，写成具体规则，再写明它负责哪些文件和接口、哪些不动、要跑哪些检查、报告里要带什么证据。整合由你负责：每份报告里至少挑一项检查自己重跑，并测试合起来的结果。干活的 Agent 说“做完了”只是一句声明，不是证据。没法派发时，自己按顺序做完各部分。

## 5. 写提示词模式

产出一段自包含的提示词，依次包含下面几块。

1. 目标和背景，写清对方不知道的上下文。
2. 范围：哪些要做、哪些不做、它负责哪些文件或系统。
3. 对方能自己检查的验收标准。
4. 选中的卡片，写成规则，填上这次任务的具体内容。
5. 预算：什么时候该停下来报告，而不是硬做下去。
6. 报告格式：证据账本，每条标准带着证据标明已验证、失败或未验证，末尾是不确定的地方。

目标是 CLAUDE.md 或 AGENTS.md 时，从 techniques.md 末尾的合并版提示词出发，只留和这个项目相关的行。

写完做一次同事测试：把提示词当成发给一个完全不了解任务的同事，对方读完能直接开工才算合格。提示词放在一个代码块里交付，后面逐行列出用了哪些卡片、为什么。

## 6. 咨询模式

每张选中的卡片写三行：在这里防的是什么失败，落到这里第一步具体做什么，做完会留下什么证据。然后用一行说明考虑过但没选的卡片和原因。最后问用户要不要按套用模式开始执行。

## 7. 收尾

最后一行列出这次用到的卡片名。
